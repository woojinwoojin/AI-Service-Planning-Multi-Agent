# 07 실시간 솔루션 시연 — 진행 문안 (2p · 100초)

공식 요구는 정상 실행이 아니다 — **"다양한 테스트 시나리오를 통한 시연 (예) Edge Case 및
예외상황에 대한 실시간 예외처리 및 에러 극복"** 이다. 정상 실행만 보여주면 요건 미달이다.

**이 프로젝트는 이 요건에 강하다.** 보여줄 예외가 전부 코드·실측 근거를 갖고 있다.

---

## 사전 준비 (발표 전, 반드시)

### 서버 기동

`.env` 에 한 줄 추가 후 재시작:
```
ENABLE_DEMO_TOOLS=1
```
```
uvicorn app.main:app --port 8000
```

⚠️ **`--reload` 금지.** 저장소가 OneDrive 안이라 동기화가 파일을 건드리면 실행 중 워크플로가 죽는다.
⚠️ **공개 Cloud Run 에서는 `ENABLE_DEMO_TOOLS=0` 을 유지한다** — 켜면 외부 사용자가 임의로
Agent 를 실패시킬 수 있다. 시연은 **로컬**에서 한다.

### 리허설 체크리스트

| # | 확인 | 통과 기준 |
|---|---|---|
| 1 | `curl localhost:8000/health` | `dummy_mode: false` · `artifact_read_mode: legacy` |
| 2 | `localhost:8000/admin` 열림 | 404 면 `ENABLE_DEMO_TOOLS` 미반영 → 서버 재시작 |
| 3 | **정상 실행 1회** (메인 UI) | KOSENA **26~28/28** · 소요 시간을 재서 적어 둘 것 |
| 4 | **장애 주입 1회** (`/admin`) | `run_status` = **`degraded`** · `fallback_reasons` 표에 항목 표시 → **`project_id` 를 적어 둘 것** |
| 5 | 메인 UI 이력에서 4번 **불러오기** | 상단 **degraded 배너** + 노드별 *"…을(를) 완성하지 못했어요"* 안내가 보이는지 **눈으로 확인** |
| 6 | 내보내기 4개 클릭 | DOCX·PPTX 열림 |
| 7 | 브라우저 확대 125~150% | 프로젝터에서 표가 읽히는지 |

> ⚠️ 5번은 **사람이 봐야 한다.** 이 환경에 node 가 없어 JS 자동 테스트가 없다.

### 장애 주입 방법 (`/admin`)

주소창에 **직접** `localhost:8000/admin` 입력(화면의 관리자 링크는 죽은 버튼이라 제거했다).

| 설정 | 값 |
|---|---|
| 실패시킬 노드 | **`kosena_model` 1개만** (권장 — 아래 이유) |
| 실패 원인 | **`혼잡`** (선택: `혼잡` \| `연결` \| `형식` \| `처리`) |
| 소요 | **약 30초~1분** (실패 노드는 LLM 호출을 건너뛴다) |

**왜 노드 1개만 실패시키나** — 이번에 `kosena` 병합 결함을 고쳤기 때문에, 이제 한 노드만 죽여도
**나머지 3개 KOSENA Agent 산출물은 그대로 남는다.** 그래서 "전부 무너짐"이 아니라 **"부분 손실 +
정직한 표기"** 라는 정확한 그림이 나온다. 수정 전에는 어차피 다 무너져서 이 시연이 성립하지 않았다.

> 참고: `/admin` 은 `/run`(동기)을 쓴다. 메인 UI 는 `/run/stream` 이다. **주입 토글은 `/admin`
> 에만 있으므로** 메인 UI 로 실행하면서 주입하려면 운영자 환경변수 경로를 써야 한다
> (`DEMO_FAIL_NODES=kosena_model DEMO_FAIL_REASON=혼잡` — 이 경로는 게이트와 무관하게 동작).
> 시연에는 `/admin` 이 낫다 — `run_status`·`fallback_reasons`·로그를 한 화면에 보여준다.

## 진행표 (100초)

| 초 | 화면 | 조작 | 나레이션 |
|---|---|---|---|
| **0–15** | 메인 UI (입력 미리 채워둠) | **실행 클릭** → 진행 표시가 흐른다 | "정상 시나리오를 실시간으로 시작합니다. 분석 Agent 4개가 동시에 돌고, 합류 후 KOSENA 산출물 4종이 순서대로 생성됩니다." |
| **15–20** | 진행 표시 | — | **"생성에 약 3분이 걸리므로, 결과는 미리 실행해 둔 것으로 이어 보겠습니다."** ← **이 한 마디 필수** |
| **20–35** | 사전 정상 결과 (탭 전환) | KOSENA 준수 표 → 근거 목록 | "KOSENA 28개 항목 중 27개 충족입니다. 근거는 전부 조회 시점이 기록돼 있습니다." |
| **35–50** | 내보내기 | DOCX·PPTX 다운로드 → **실제로 열기** | "결과는 Word 와 PowerPoint 로 바로 나옵니다. 표와 본문이 실제 파일에서 정상 렌더링됩니다." |
| **50–85** | 🎬 이력에서 **주입 실행 불러오기** | degraded 배너 → 노드별 미완성 안내 | (아래 전문) |
| **85–100** | Edge Case 목록 슬라이드 | — | "검색 차단·예산 상한·스키마 불일치·요청 상한도 같은 방식으로 처리합니다. 공통 원칙은 하나입니다 — **완주하되 숨기지 않는다.**" |

### 50–85초 나레이션 (약 170자) — 이 구간이 요건의 핵심

> "이번엔 예외 상황입니다. **특정 Agent 를 일부러 실패시켜** 미리 실행해 둔 기록입니다.
> 보시면 실행 상태가 `success` 가 아니라 **`degraded`** 로 남아 있고, 어느 단계가 왜 실패했는지
> **원인이 항목으로 표시**됩니다. 중요한 건 **나머지 Agent 는 완주했다**는 점입니다 — 하나가
> 죽어도 파이프라인이 멈추지 않고, 대신 **완성하지 못한 부분을 그대로 알려줍니다.**
> 실패를 성공으로 덮지 않는 것이 이 시스템의 설계 원칙입니다."

**화면에서 손가락으로 짚을 것 3개**: ① `degraded` 배지 ② 노드별 *"…을(를) 완성하지 못했어요"*
안내와 원인 ③ 나머지 KOSENA 항목이 여전히 충족돼 있는 것

## p1 슬라이드 — 시연 안내

### 제목
**"정상 1건 + 예외 1건 — 실패를 어떻게 다루는지까지"**

### 슬라이드
| 시나리오 | 확인 항목 |
|---|---|
| ① 정상 실행 | 실시간 진행 → KOSENA 준수 → 근거·검증 → DOCX/PPTX |
| ② **Agent 강제 실패** | `run_status = degraded` · `fallback_reasons` 표기 · **나머지 Agent 완주** |

**하단 한 줄**: 시연 환경 = 로컬(`ENABLE_DEMO_TOOLS=1`). 공개 배포는 장애 주입을 **끈 상태**로 운영합니다.

## p2 슬라이드 — Edge Case 목록

### 제목
**"예외를 어떻게 처리하는가 — 완주하되 숨기지 않는다"**

| 예외 상황 | 처리 | 근거 |
|---|---|---|
| **Agent 노드 실패** | 폴백으로 완주 + `degraded` 유지 + `fallback_reasons`(혼잡/연결/형식/처리) | `app/services/demo.py` · **라이브 시연** |
| **검색(Tavily) 완전 차단** | 근거 0건에도 KOSENA **26/28 완주** — 출처 항목만 미충족 | 실측 (`docs/동결_기록.md`) |
| **LLM 이 스키마와 다른 형태 반환** | Agent `_validate()` 가 중립값으로 흡수 + 표시 계층 `displayText()` | 실제로 화면이 죽었고 고쳤다 |
| **실행 예산 상한 도달** | 이후 LLM 호출을 생략하고 폴백 완주 (**강제 중단 아님**) | `BUDGET_MAX_*` |
| **프롬프트 인젝션** (검색 결과에 지시문) | 검색 결과를 `<검색결과>` 구획으로 감싸고 "지시 무시" 명시 | `templates.py:16-19` · `competitor.py:94-99` |
| **공개 주소 남용** | IP 5회/시간 · 전역 100회/일 · $2/일 → 429 | `public_guard` |
| **`/revise` 가 실패 표기를 지움** | 발견 → 수정 (#130) | **"에러 극복" 서사** |
| **UI 경로가 산출물을 잃음** | 발견 → 수정 + 경로 대조 테스트 8개 (#132) | 발표 전날 |

**마지막 두 줄이 이 표의 핵심**이다 — 예외를 처리하는 것뿐 아니라 **예외 처리 자체의 결함을 찾아
고친 이력**이 있다. 이건 "동작합니다"보다 강한 주장이다.

## 실패 대비 3단

| 단계 | 상황 | 대응 |
|---|---|---|
| 1 | 정상 실행이 느리다 | 예정대로 20초에 사전 결과로 넘어간다(어차피 그 계획이다) |
| 2 | 라이브 실행이 아예 실패 | 이력에서 리허설 정상 실행을 불러온다. 로컬은 이력이 영속이다 |
| 3 | 서버·네트워크 사망 | `presentation-assets/exports/*` (DOCX·PPTX) + `demo-results/deployed-00009-*` |

**근거가 0건으로 나와도 소재다**: *"지금 검색이 실패했습니다. 그런데 KOSENA 는 붕괴하지 않고
출처 항목만 미충족이 됩니다 — 검색을 완전히 차단해 측정했고 26/28 이 나왔습니다."*

## ⛔ 하지 말 것

| | 왜 |
|---|---|
| **20초의 "미리 실행해 둔 결과" 고지를 빼기** | 사전 결과를 실시간 결과로 보이게 하는 것 = 이 프로젝트 원칙 위반 |
| **`/projects` 목록을 화면에 띄우기** | 인증이 없다. 리허설·개발 중 만든 실행이 전부 노출된다. `project_id` 로 직접 진입 |
| **공개 URL 에서 장애 주입 시연** | 외부 사용자가 임의로 Agent 를 실패시킬 수 있다 |
| **"PPTX 57장을 자동 생성합니다" 강조** | KOSENA 권장이 15~20장이라 분량 제어 실패로 읽힌다. Q&A 에서 한계와 함께 |
| **터미널을 화면에 넣기** | API 키가 흐를 수 있다 |
| **발표 성공을 라이브 실행 완료에 의존시키기** | 외부 API 상황에 따라 늦어진다. Q&A 때 끝나면 **보너스**로만 쓴다 |

## 예상 질문

- **"실시간이 아니라 미리 만든 결과 아닌가요?"** → 실행은 실시간으로 시작했고 진행 상태를
  보셨습니다. 생성에 약 3분이 걸려 결과만 사전 실행분으로 이어 보였습니다. **지금 시작한
  실행이 끝나면 바로 보여드릴 수 있습니다.**
- **"일부러 실패시킨 건 진짜 실패가 아니잖아요?"** → 주입 지점은 **LLM 호출 단계**입니다
  (`llm._timed_invoke` 가 실제 `LLMError` 를 던집니다). 그 뒤는 실제 장애와 **완전히 같은
  폴백 경로**를 탑니다 — `fallback_reasons` 에 기록되는 방식도 동일합니다.
- **"한 Agent 가 실패하면 문서 품질은요?"** → 해당 항목은 KOSENA 자체점검에서 미충족으로
  보고되고, 화면과 문서에 **완성하지 못한 부분으로 표시**됩니다. 빈칸을 그럴듯한 문장으로
  채우지 않습니다.
- **"복구는 자동으로 되나요?"** → LLM 호출은 1회 재시도합니다. 그 뒤에도 실패하면 폴백으로
  완주하고 **상태를 `degraded` 로 남깁니다.** 자동 재실행은 하지 않습니다 — 비용이 들고,
  실패를 사용자에게 알리는 편이 맞다고 판단했습니다.
