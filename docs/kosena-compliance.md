> 근거: `KOSENA_AI_서비스기획.pdf`(21쪽). 쪽수는 원문 대조용으로 각 항목에 표기했다.

> 갱신: 2026-07-27

## 왜 이 문서가 있는가

과제 체크포인트 3은 **"제공된 기획 방법론 템플릿(KOSENA)을 준수하는가"** 다. KOSENA 는 문서
디자인 템플릿이 아니라 **반드시 거쳐야 하는 분석 프레임워크와 산출물 구조**를 규정하고,
평가표(p20)도 프레임워크 정확도·Lean Canvas 일관성·TAM/SAM/SOM 교차검증·VPC Fit·
MVP/Epic-Story-AC/와이어프레임을 **직접** 본다.

점검 결과 **현재 파이프라인은 체크포인트 1·2 는 충족하지만 체크포인트 3 은 부분 충족**이다.
이 문서는 그 격차를 **숨기지 않고 항목 단위로 고정**한다. 평가에서 '표면적 적용'보다 나쁜 것은
'무엇이 빠졌는지 모르는 상태'다.

### 남은 것 — 본문 분량 (정직 표기)

자동 생성 본문은 더미 기준 **약 12.2쪽**(v2 실 LLM 측정 시점 11.9쪽 — 이후 부록 2개 추가로 늘었다)이고
요건은 30~50쪽이다.
격차의 성격을 분명히 해 둔다:

- **분량을 위한 분량은 넣지 않았다.** 같은 내용을 늘려 쓰거나 표를 쪼개 쪽수를 맞추는 것은
  평가표의 '문서 완성도'(논리·시각화·인용)와 오히려 어긋난다.
- KOSENA 가 상정하는 30~50쪽은 **팀이 1차 자료(인터뷰·설문)와 부록·근거 자료를 붙인 분량**
  으로 보인다(p4 의 제출 원칙이 정량 주장의 1차 자료 뒷받침을 함께 요구한다).
- 따라서 이 격차는 **자동 생성으로 메울 성질이 아니라, 사람이 리서치 결과를 덧붙여 채우는
  부분**이다. 도구는 그 골격(7종 산출물 구조·프레임워크·표)을 제공한다.

> 분량 추정은 **줄 수 기준**이다(A4·11pt 기준 45줄/쪽). 글자 수로 세면 표가 많은 문서에서
> 크게 빗나간다 — 실측한 산출물은 494줄 중 183줄이 표 행이었고 글자 기준 8.1쪽 vs
> 줄 기준 11.0쪽으로 갈렸다. 정확한 쪽수는 렌더러가 정하므로 어디까지나 추정치다.

> ⚠️ **비용·지연**: KOSENA 노드 4개가 **순차** 실행이라 LLM 호출이 실행당 +4(13~15 → 17~19),
> 지연은 +20~30초다. `kosena_industry` 와 `kosena_research` 는 서로 독립이라 병렬화 여지가
> 있지만, 정확성을 우선해 순차로 뒀다.

### ⚠️ 출처 검사의 범위 — '주장별 검증'이 아니다

`sources_cited` 는 **실행 전체에 인용된 출처가 있는지**만 본다. 그래서 다음 상태에서도 충족이다:

    Research Agent 가 출처 URL 5건을 모았다
    그런데 TAM/SAM/SOM · 경쟁사 정보 · 정책 변화에 **직접 연결된 근거는 없다**
    → 출처 항목 충족

14섹션 기획서 쪽에서는 `verify` 가 주장별로 `evidence_ids` 를 붙이고 화면·문서에 표시하지만,
**KOSENA 산출물의 필드별(TAM·경쟁사·정책) 근거 연결은 아직 없다.** 판정 detail 이 그 경계를
직접 적는다(`… 실행 전체의 출처 존재 검사이며 KOSENA 산출물 항목별 근거 연결은 미구현`).

**발표에서 쓸 표현**: "실행 전체의 출처 존재를 검사한다"는 맞고, "각 KOSENA 주장별로 출처를
검증한다"는 **틀렸다**. 후속 범위는 `kosena_research` 출력에 `evidence_ids` 를 받아
레지스트리에 실제 있는 id 만 남기고, 비면 '직접 연결된 근거 없음'으로 적는 것이다 —
코드가 임의로 "이게 TAM 근거겠지"를 추론해 부록을 만들면 그것도 허위다.

## 구조적으로 채울 수 없는 항목 (정직 표기)

평가표(p20) **'고객 이해'** 우수 기준은 *1차 인터뷰 + 설문 + 정성 통찰*이고, 페르소나 정의도
*인터뷰 5명 + 설문 100명*을 예로 든다(p12). **AI 파이프라인은 이를 만들 수 없다.**

지어내면 KOSENA 원칙(*정량 주장은 1차 자료로 뒷받침*, p4)에 정면으로 위배된다. 따라서 목표는
'충족'이 아니라 **가설임을 명시하는 것**이고, 검사도 그 표기 여부를 본다
(`hypothesis_labeling`). 예:

> 본 페르소나는 웹 리서치에 기반한 **가설형 페르소나**이며 실제 인터뷰로 검증되지 않았습니다.
> SOM 은 1~3년차 점유율 **가정**을 사용한 추정치이며 실제 점유율이 아닙니다.

이 태도는 PDF 의 결론과도 맞는다 — *"완벽한 기획서가 아니라 의사결정 가능한 가설을 만든다"*(p21).

## 어떻게 메웠나 (KOSENA Agent 4종)

착수 전 판단은 *"기존 산출물을 재조립하면 된다"* 였는데 **절반만 맞았다** — 재료 자체가 없는
항목이 다수였다(Lean Canvas 9블록 중 6블록·CJM·TAM/SAM/SOM·VPC·MOSCOW·Epic-Story). 이들은
포맷팅이 아니라 **새 분석**이 필요했다. 다만 새 Agent 10개가 아니라 **4개**로 충분했다.

| Agent | 담당 |
|---|---|
| `kosena_industry` | Critical Uncertainties Top3 · Porter · Value Chain · KSF 5 · 시사점 3 |
| `kosena_model` | HMW 5 · 아이디어 25+ · **압축 후보 3** · 컨셉 1 · Lean Canvas 9블록 · 핵심 가설 3 |
| `kosena_research` | 페르소나 2종 · CJM · TAM/SAM/SOM 교차검증 · 경쟁사 3/2/1 · 비교항목 10+ · **경쟁사 비교표** · 포지셔닝 맵 |
| `kosena_roadmap` | VPC · 기능 5~7 · Use Case 3 · MOSCOW · Kano · MVP · Epic-Story-AC · 마일스톤/KPI · 와이어프레임 |

**PDF p7 의 프레임워크 체인이 그대로 쓰였다** —
> 거시환경(PESTEL) → 산업환경(Porter) → 자사환경(SWOT) → KSF 도출

이 구조가 이 프로젝트의 **Artifact `depends_on` 모델과 대응**해서, 새 Agent 를 그 위에 얹는
것으로 배선이 끝났다. 4개 노드는 순차이고(`industry → model → research → roadmap`), 뒤 노드가
앞 결과를 이어받아야 평가표의 'Lean Canvas 블록 간 일관성'·'VPC Fit'이 성립한다.

**공통 설계 원칙 — 모자란 개수를 지어내 채우지 않는다.** KSF 가 4개면 4개로 두고 검사가 '부분
충족'을 말하게 한다. 빈 문자열로 5개를 맞추면 검사만 통과하고 문서엔 빈칸이 남는, 가장 나쁜
결과가 된다.

**프롬프트는 KOSENA 표준 5단 구조**([역할][입력][요구사항][출력 형식][검증 조건], p19)로
작성했다 — 형식 준수 자체가 'AI 활용' 평가 항목이라 테스트로 고정했다.

> **실측에서 잡은 회귀**: 실 LLM 이 경쟁사를 문자열이 아니라 **객체 배열**로 반환해 분류가
> 통째로 0/0/0 이 됐다. 둘 다 받아 이름만 뽑도록 고쳤다 — 형식 차이로 내용을 잃는 것이 가장
> 아까운 실패다. 더미에서는 절대 나오지 않았을 종류다.

## 산출물 (p5 의 7종 + p4 의 제출 형식)

`kosena_doc` 이 State 에서 **7종 산출물 Markdown** 을 조립하고, 기존 익스포터가 그대로 문서로
바꾼다. `POST /run/save` 가 함께 저장한다.

| 파일 | 내용 |
|---|---|
| `<이름>-KOSENA.md` / `.docx` | 7종 산출물 본문(면책 문구·준수 현황·AI 로그 포함) |
| `<이름>-KOSENA-발표.pptx` | 발표자료 **20슬라이드**(요건 15~20쪽 충족) |
| `<이름>-AI활용로그.md` | AI 활용 로그(p4: '별도 파일 첨부') |
| 기존 `<이름>.md/.docx/.pptx/.json` | 14섹션 기획서 — **그대로 유지** |

> **왜 기존 문서를 재구성하지 않았나.** `final_draft`(14섹션)를 KOSENA 구조로 갈아엎으면
> `sections.py` 왕복 byte 동일 불변식 · `section_revise`(PR-7) · `quality_gate` 의 '서식 정상'
> 체크 · `parallel_bench` 가 한꺼번에 깨진다. 반면 `docx_bytes(markdown)`·`pptx_bytes(markdown)`
> 는 **markdown 만 받는 순수 함수**라, 별도 조립본을 같은 함수에 넣으면 기존 경로를 한 줄도
> 건드리지 않고 산출물이 나온다.

## 판정과 문서는 왜 두 번 조립되나 (순환 의존)

판정과 문서는 서로를 필요로 한다:

    판정(`kosena.evaluate`)  → 조립된 본문(`kosena_plan`)에서 분량·가설 표기를 잰다
    조립(`kosena_doc.build`) → 판정 결과를 준수 현황 표로 싣는다

어느 쪽을 먼저 둬도 한쪽은 헛것을 본다. 그래서 `workflow._finalize_kosena` 가
**조립 → 판정 → 재조립 → 발표자료** 순으로 끊는다. `_compliance_section` 이 판정 전에도 같은
행 수(항목 수는 `REQUIREMENTS` 로 고정)로 렌더링하므로 두 조립의 줄 수가 같고, 따라서 판정이
말하는 분량이 **실제로 내려받는 문서의 분량**이다.

> **고치기 전에 실제로 어긋나 있었다.** 조립 시점에 판정이 없으면 `build()` 가 즉석 판정을
> 돌렸는데, 그때는 `kosena_plan` 이 아직 State 에 없어 **14섹션 초안**을 기준으로 분량·가설
> 표기를 쟀다. 더미 1회 실측에서 본문에는 `25/28`, 최종 State 에는 `26/28` 이 실렸고
> (`hypothesis_labeling` 이 갈렸다 — 14섹션 초안에는 가설 표기 문구가 없다), 발표자료에는
> `(미판정)` 이 그대로 남았다. 테스트로 고정했다(`test_document_reports_the_same_compliance_as_the_final_state`).

`/revise` 후에도 같은 함수를 부른다(`rerun_finalizers`). 그러지 않으면 14섹션 기획서만 수정되고
KOSENA 문서·준수 판정·AI 로그는 수정 전 내용으로 남는다 — 화면이 그 값을 그대로 보여주므로
옛 산출물이 눈에 보인다. LLM 호출이 없어 `/revise` 지연에는 사실상 영향이 없다.

## 어디서 볼 수 있나 (응답·화면)

산출물이 State 에만 있으면 평가자에게는 없는 것과 같다. 세 경로 모두에서 보인다:

| 경로 | 내용 |
|---|---|
| `POST /run`·`/run/stream`·`/revise` 응답 | `kosena` · `kosena_compliance` · `kosena_plan` · `kosena_deck` · `ai_usage_log` |
| 화면 **STEP 4 · KOSENA 방법론 산출물** | 준수 자체점검(항목별 판정 28건) · AI 활용 로그 · 본문 · 내려받기 4종 |
| 저장·재조회 | `_RUN_KEYS` 에 포함 — 이력에서 불러와도 STEP 4 가 그대로 뜬다 |

내려받기는 **기존 익스포터를 그대로 쓴다**(`/export/docx`·`/export/pptx` 는 markdown 을 받는다).
AI 로그만 `/export/ai-log` 를 새로 뒀는데, Markdown 조립을 `ai_log.to_markdown` 한 곳에만 두어야
문서 안의 로그와 내려받은 파일이 갈라지지 않기 때문이다.

## AI 활용 로그 — 무엇을 남기고 무엇을 안 남기는가

남기는 것: system 프롬프트(코드로 버전 고정)·5단 구조 준수 여부·입력 Artifact 목록·응답
산출물·검증 결과(`status`)·**채택 여부**.

**user 프롬프트 원문은 남기지 않는다** — 앞 단계 결과를 기계적으로 이어 붙인 것이라 입력
목록·응답과 중복이고, 웹검색 스니펫(신뢰할 수 없는 외부 텍스트)이 그대로 실려 로그가 비대해진다.

'채택 여부'는 실제 판정에서 온다. 특히 **`reverted_from_revision`** — AI 재작성이 초안보다
낮게 평가돼 되돌린 기록이라, *"AI 응답을 그대로 쓰지 않았다"*(p4)는 것을 가장 분명하게 보여 준다.

## 이 검사를 쓰는 법

```bash
python run_kosena_check.py            # 더미 1회 실행 → 현황 리포트(무비용)
python run_kosena_check.py --real     # 실 LLM 1회(비용 발생) — 출처 항목까지 실측
```

실행 결과에는 `state["kosena_compliance"]` 로 항상 포함되고, 저장·재조회에도 남는다
(`_RUN_KEYS`). 옛 기록은 재조회 시 소급 판정된다.
