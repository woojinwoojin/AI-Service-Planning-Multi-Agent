# AI 서비스 기획 보조 **Multi-Agent**

### 근거를 모으고, 검증하고, 출력 가능한지 판정하는 워크플로

<small>2026-07-26 · 발표자료 2차</small>

---

## 오늘 말씀드릴 것

**1. 문제** — AI 기획 초안은 그럴듯한데 근거를 확인할 수 없다

**2. 해법** — 근거를 구조로 붙들어 두는 파이프라인

**3. 증거** — 네 가지 축으로

| 축 | 한 줄 |
|---|---|
| 근거 | 출처 URL **0 → 평균 5개** |
| 신뢰도 | 근거 없는 주장 **허위 통과 0/4** |
| 성능 | 측정으로 병목을 짚고 **연속 단축** |
| 운영 | 출력 가능 여부를 **판정**하고, 폭주를 **막는다** |

---

## 1. 문제

LLM에 "기획서 써줘"라고 하면 **읽기엔 완벽한 문서**가 나옵니다.

그런데 이런 문장이 섞입니다.

---

## “2022년 조사에 따르면 60%가… 70%는…”

<br>

### 출처가 없습니다. 확인할 방법도 없습니다.

<br>

기획 문서에서 이건 단순 오류가 아니라 **문서 전체의 신뢰를 무너뜨리는** 문제입니다.

---

## 2. 제안 서비스

아이디어 한 줄 → **근거가 붙은 14섹션 기획서**

- 실제 웹 검색으로 **출처를 수집**하고
- 역할이 다른 Agent들이 **분석·작성·검토**하고
- 작성된 주장을 **수집한 근거와 대조**하고
- 마지막에 **"이대로 내보내도 되는지" 판정**합니다

산출물: Markdown · JSON · **Word** · **PowerPoint**

---

## 3. 이번 발표의 핵심 관점

> **Multi-Agent의 가치는 "점수"가 아니라 "추적 가능한 근거"에 있다.**

단일 LLM은 검색을 하지 않으므로 출처가 **구조적으로 0**입니다.
모델을 더 좋은 것으로 바꿔도 이 격차는 뒤집히지 않습니다.

그래서 이 발표는 **점수 자랑이 아니라, 근거를 어떻게 붙들어 두는지**에 대한 이야기입니다.

---

## 4. 워크플로 (18개 노드)

**입력·조사** → preprocess → Research(웹검색) → research_gap(근거 공백 보강)

**분석**(독립 분기 **병렬**) → Competitor · Customer · PESTEL · SWOT · Business Model · Risk

**작성·개선** → Draft → Reviewer → **3분기 라우팅**
<small>① 문제 섹션만 수정 · ② 전체 재작성 · ③ 수정 없음 — 자동 재작성은 **1회 상한**</small>

**마무리** → 조건부 Polish → Final Reviewer → **최고 버전 채택** → Verify → 품질 게이트

<br>

- 오케스트레이션: LangGraph `StateGraph` (직렬/병렬 두 그래프)
- 개별 Agent 실패가 전체 중단으로 이어지지 않도록 **fallback 설계**

---

## 5. 근거를 어떻게 붙들어 두는가 <small>[구조]</small>

검색 결과를 그냥 문서에 붙이면, 나중에 **어느 주장이 어느 근거에서 나왔는지** 알 수 없습니다.

**Evidence Registry** — 모든 실제 검색 결과를 단일 저장소로

```
{ evidence_id: "ev1", source_agents: ["research"], queries: [...],
  url, title, snippet, used_by_claims: ["c3", "c7"] }
```

- `evidence_id`는 **URL 최초 등장 순서**로 결정 → 재현 가능
- 검증 단계가 주장마다 `evidence_ids`를 지목 → **주장 ↔ 근거 역방향 추적**
- 결과 화면은 **인용이 많은 출처를 위로** 정렬해 보여줍니다

---

## 6. Agent 산출물의 표준 봉투 <small>[구조]</small>

**Artifact Contract** — 각 Agent 결과를 같은 형태의 객체로

```
{ artifact_id, artifact_type, owner_agent,
  content,            ← Agent별 결과(내부 형식은 그대로)
  evidence_ids[],     ← 직접 사용한 근거
  depends_on[],       ← 어느 산출물을 입력으로 썼는지
  target_sections[],  ← 기획서의 어느 섹션을 책임지는지
  status }
```

7개 Agent 전부 적용 · 의존 관계 자동 기록(예: SWOT ← Research + Competitor)

> ⚠️ **현재 단계**: 기존 구조와 **병행 기록** 중이며, 읽기 경로 기본값은 아직 기존 방식입니다.
> "이슈를 담당 Agent에게 보내 그 부분만 다시 실행"의 **기반**을 깐 상태입니다.

---

## 7. 비교 실험 — 조건 통제

**고정한 것**: 동일 입력 · 동일 출력 서식 · 동일 평가표 · 동일 심판 모델(gpt-4o-mini)

**표본**: 6개 주제 · 결과당 3회 평가 평균

**고정하지 않은 것(의도적)**: 단일 방식과 Multi-Agent 방식의 **검색·호출·검토 구조**

> 즉 이 비교는 "단일 프롬프트 1회" vs "**웹검색 + 단계별 분석·검토를 포함한 파이프라인 전체**"입니다.

---

## 8. 가장 명확한 차이 — 고유 출처 URL

<br>

### 단일 프롬프트 **0개**  →  Multi-Agent **평균 5개**

<br>

- LLM 평가 총점: 84.9 → **86.5 (+1.6)**
- 6개 주제 중 **5개**에서 Multi-Agent 우위 <small>(1개는 −0.3 근소 열세)</small>

> 💬 헤드라인은 **출처 0 → 5**. 점수는 보조입니다.
> 작은 심판 모델은 "유창하지만 근거 없는 글"과 "실제 인용된 글"을 잘 구분하지 못해 점수 격차가 작게 나옵니다.

---

## 9. 생성 모델을 바꿔도 출처 차이는 유지

| 생성 모델 | 점수 차이 | 출처(단일 / Multi) |
|---|---|---|
| gpt-4o-mini | +1.8 | 0 / 평균 5 |
| gpt-4o | +1.6 | 0 / 평균 5 |

- 모델이 강해지면 **점수 격차는 오히려 줄어듭니다**
- 그런데 **출처 격차는 그대로**

> 💬 **"강한 모델도 스스로 검색하지는 않는다."**
> 점수 격차가 줄어드는 것이 오히려 이 구조의 가치를 보여줍니다.
> ⚠️ 3주제 기반 — 일반화가 아니라 **방향성 확인**입니다.

## 10. 근거를 모은 다음 — 검증 <small>[신뢰도]</small>

출처를 붙이는 것과, 그 출처가 **주장을 실제로 뒷받침하는지**는 다른 문제입니다.

**주장을 세 가지로 나눕니다**

| 유형 | 예 | 검증 |
|---|---|---|
| 사실 | "국내 시장이 증가 추세다" | ✅ 근거와 대조 |
| 추론 | "따라서 성장할 것으로 예상된다" | 대상 아님 |
| 제안 | "본 서비스는 …를 제공한다" | 대상 아님 |

**사실 주장만** 검증하고, 결과를 네 가지로 구분합니다
→ `supported` · `unsupported`(근거에 없음) · **`contradicted`(근거가 반대)** · `uncertain`

---

## 11. 검증이 실제로 걸러내는가 <small>[신뢰도]</small>

**Ground Truth 스모크셋 10건**(균형 구성) — 정답을 아는 주장으로 판정기를 시험

| 항목 | 결과 |
|---|---|
| **허위 통과**(근거 없거나 반대인데 supported) | **0 / 4** |
| 반대 근거 탐지 | 2 / 2 |
| 근거 있는 주장 통과 | 2 / 2 |
| 주장 유형 분류 정확 | 9 / 10 |
| 추론·제안을 검증 대상에서 제외 | 3 / 3 |

<small>gpt-4o-mini · 표본 10건 · 비율이 아니라 n/N으로 보고</small>

> ⚠️ **정직한 한계**: 표본 10건입니다. 그리고 `unsupported`는 **'거짓'이 아니라 '수집한 검색 요약에서 확인되지 않음'**입니다 — URL 원문까지 대조하지는 않습니다(향후 과제).

---

## 12. 출력 가능 여부를 판정한다 <small>[운영]</small>

점수만 보여주는 대신, **이대로 내보내도 되는지**를 판정합니다.

```
release_ready =
      총점 ≥ 80
  and 치명 이슈 = 0
  and 주요 이슈 ≤ 1
  and 서식 정상(14섹션)
  and 사실 주장 근거 충족률 ≥ 0.8
  and 반대 근거 = 0
```

- 통과/미통과와 **미해결 항목**을 결과 화면 최상단에 노출
- 사실 주장이 0건이면 충족률이 자동 1.0이 되는 허점 → **"검증 없음(N/A)"으로 구분 표시**

> 💬 임계값은 **사람 기획서 보정 전 잠정값**입니다(과장하지 않기).

## 13. 폭주를 막는다 <small>[운영]</small>

AI 파이프라인은 조용히 비용·시간을 태울 수 있습니다.

| 상한 | 기본값 | 초과 시 |
|---|---|---|
| LLM 호출 수 | 50회 | **호출을 생략하고 fallback** |
| 비용 | $1.0 | 〃 |
| 실행 시간 | 10분 | 〃 |

- **강제 중단이 아니라 관통 보장** — 상한에 걸려도 문서는 끝까지 나오고, 사유를 표시합니다
- 추가 조사(동적 실행)도 상한 안에서만: 추가 검색 최대 2회 + 보강 LLM 1회
- 병렬 실행에서도 정확히 세도록 **원자적 예약** 방식

## 14. 측정으로 병목을 짚는다 <small>[성능]</small>

**기준선 baseline-v1** — 6주제 · 24회 · gpt-4o-mini · AB/BA 교차

| 지표 | 직렬 | 병렬 | 변화 |
|---|---|---|---|
| 전체 wall(중앙값) | 127.4s | **106.8s** | **−16.1%** |
| 분석 구간 | 35.7s | **21.0s** | **−41%** |

- 품질·비용 **동등**(14섹션 100% · fallback 0 · 24회 전부 success · 평균 ~$0.01/실행)
- 근거 확인율 85.3%(185/217)
- 남은 병목이 **문서 재생성 구간**임을 이 측정으로 특정

## 15. 병목을 실제로 줄였다 <small>[성능]</small>

**① 전체 재작성 → 문제 섹션만 수정**
Reviewer가 섹션 ID로 문제를 지목하면, 문서 작성 Agent가 **그 섹션만** 다시 쓴다 — 나머지 섹션은 원문 그대로 유지 (실패 시 전체 재작성으로 자동 복귀)

**② 조건부 Polish** — 표현 문제가 없으면 편집 단계를 생략

**개편 후 측정** — 3주제 · 12회

| 단계 | 직렬 | 병렬 |
|---|---|---|
| 전체 wall(중앙값) | 80.8s | **64.3s** |
| Polish 단계 | \~0.1ms(대부분 생략) | \~0.1ms |
| 재작성 구간 | 7.5s | **5.8s** |

> ⚠️ **주의**: 기준선(6주제)과 **주제 구성이 달라 두 표를 이어 붙이면 안 됩니다.**
> 각 표 **안에서의** 비교만 유효합니다.

## 16. Polish를 생략해도 품질이 떨어지지 않는가 <small>[성능]</small>

빠르게 만들었다면, **품질 손해가 없는지**도 확인해야 합니다.

**블라인드 A/B** — 생략본 vs 강제 편집본을 위치 교차해 심판에게 제시

| 결과 | 건수 |
|---|---|
| 편집본 우세 (= 생략이 손해) | **0 / 4** |
| 생략본 우세 | 0 / 4 |
| 차이 없음 | **4 / 4** |

> 💬 "빨라졌다"만 말하지 않고 **"빨라졌는데 나빠지지 않았다"**까지 확인했습니다.
> ⚠️ 표본 4건 · 심판 1회 — 소표본입니다.

## 19. 정직한 범위 (과장하지 않기)

- 비교 실험은 **Agent 분업 효과와 웹 검색 효과가 함께** 측정된 값입니다
- 출처 URL 수는 **포함 개수**이며 내용의 사실성을 보장하지 않습니다
- 검증은 **수집한 검색 요약과의 일치**이지 URL 원문 대조가 아닙니다
- 다중 모델(3주제) · GT(10건) · Polish A/B(4건) 모두 **소표본**입니다
- 품질 게이트 임계값은 **사람 기획서 보정 전 잠정값**입니다

> 💬 이 장을 넣는 이유: 숫자보다 **숫자의 범위를 아는 것**이 신뢰를 만든다고 봤습니다.

## 20. 한계 · 향후 계획

1. **URL 원문 대조 검증** <small>(현재는 검색 요약 기준)</small>
   → 주장 ↔ 원문 문장 직접 비교 · 출처 간 충돌 탐지

2. **동일 검색자료 기준선 추가**
   → 웹 검색 효과와 분업 효과를 **분리** 측정

3. **사람 기획서 기준 보정**
   → 품질 게이트 임계값을 잠정값에서 **실측 기반**으로

4. **Artifact 기반 선택적 재실행**
   → 이슈를 담당 Agent에게 보내 **바뀐 부분만** 다시 실행

## 21. 마무리

**문제** — 그럴듯하지만 근거를 확인할 수 없는 AI 기획 초안

**해법** — 근거를 **구조로 붙들어 두는** 워크플로

## 부록 E — 예상 질문

**Q. 결국 검색이 다 한 것 아닌가?**
맞습니다. 그래서 §19에 그렇게 적었습니다. 분업 효과만 분리하려면 **동일 검색자료를 준 단일 LLM** 기준선이 필요하고, 다음 과제로 두었습니다.

**Q. 표본이 너무 작지 않나?**
작습니다. 그래서 비율 대신 **n/N**으로 보고합니다. 다만 헤드라인(출처 0 vs 5)은 **검색 도구 유무에서 오는 구조적 차이**라 표본에 흔들리지 않습니다.

**Q. `unsupported`면 틀린 건가?**
아닙니다. **"수집한 검색 요약에서 확인되지 않았다"**입니다. URL 원문 대조는 향후 과제입니다.

**Q. 왜 심판도 LLM인가?**
같은 문서를 여러 번 채점해 **변동성(σ)**을 함께 보고하고, 작성 모델과 **심판 모델을 분리**해 자기 채점 편향을 줄였습니다. 사람 기준선 보정은 다음 단계입니다.

**Q. 실제로 운영할 수 있나?**
품질 게이트·예산 상한·CI 4게이트·Docker까지는 되어 있고, **실 호스트 배포는 아직 연결 전**입니다.
