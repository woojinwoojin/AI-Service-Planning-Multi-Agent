# 05 프로젝트 핵심 체크포인트 — 슬라이드 문안 (4p · 110초)

산업체 파트너 멘토의 현안 기준표와 대조되는 섹션이다. **배점이 가장 큰 구간이므로 시간을 깎지
않는다.** 모든 수치는 `docs/실측_표본_통계.md`(N=7)와 `docs/평가기준_매핑표.md` 에서 왔고,
단일 실행을 인용할 때는 **실행 id·측정일·주제를 함께** 말한다.

나레이션은 한국어 기준 **약 5자/초**로 잡았다. 괄호 안 글자 수를 넘기면 시간이 밀린다.

---

## p1 — Pain Point ↔ 해결 대응 (30초)

### 제목
**"사람이 오래 걸리던 세 가지를, 검증 가능한 형태로"**

### 슬라이드 (좌: Pain Point / 우: 대응)

| Pain Point | 대응 | 상태 |
|---|---|---|
| 시장조사에 시간이 많이 든다 | Research + 분석 Agent 6종이 병렬로 조사·분석 | ✅ |
| 기획서 작성이 오래 걸리고 형식이 흔들린다 | KOSENA 방법론 **28개 항목**을 코드로 자체점검 | ✅ |
| **출처가 남지 않아 검증이 불가능하다** | Evidence Registry — 근거마다 `evidence_id`·조회 시점 기록 | ✅ |
| AI 답변을 그대로 믿게 된다 | 심판 모델 분리 + **재작성본이 낮으면 초안으로 되돌림** | ✅ |

**하단 한 줄(작게)**: 자율 계획 수립 ❌ — 그래프는 고정이다. 동적 위임은 근거 공백에 대한 추가 검색(상한 2)까지.

### 나레이션 (약 145자)
> "세 가지가 오래 걸립니다 — 시장조사, 기획서 작성, 그리고 출처 관리입니다. 앞의 둘은 자동화가
> 흔하지만, 저는 **세 번째를 중심에 뒀습니다.** 근거마다 어디서 언제 가져왔는지를 남기지 않으면
> 결과를 검증할 수 없습니다. 그래서 이 시스템은 문서와 함께 **근거 목록을 산출물로 냅니다.**"

## p2 — 성능 · 비용 · 토큰 (30초)

### 제목
**"실 LLM 7건 반복 측정 — 주제를 바꿔가며"**

### 슬라이드 (측정 조건을 반드시 함께)
`gpt-4o-mini`(심판 동일) · `WORKFLOW_MODE=parallel` · Tavily 검색 정상 · **주제 7종 · 각 1회** · 총 약 $0.15

| 지표 | 평균 | 범위 |
|---|---|---|
| **KOSENA 준수** | **26.4 / 28** | **26 ~ 27** |
| 실행 비용 | **$0.0216** | $0.0162 ~ 0.0239 |
| 소요 시간 | **166초** | 148 ~ 178 |
| 토큰 | 104,190 | 69,292 ~ 119,647 |
| LLM 호출 | 18.4회 | 17 ~ 19 |
| 근거 건수 | 16.7건 | 9 ~ 19 |

### 나레이션 (약 150자)
> "주제 하나로는 그 값이 재현되는지 알 수 없어서, **데이터 가용성이 서로 다른 7개 주제로 반복
> 측정**했습니다. KOSENA 준수는 **26에서 27**, 평균 26.4입니다. 실행당 2센트, 166초, LLM 18회
> 입니다. 표본이 7건이라 평균보다 **범위**를 보시는 게 맞습니다."

### ⛔ 금지
- "27/28을 달성했습니다" → 7건 중 **3건만** 27
- "실행당 $0.022입니다"(단정) → 범위와 함께
- "26에서 27로 개선" → 별개 측정. 코드는 동일

### 예상 질문
- **"왜 26과 27이 섞이나요?"** → 직접 경쟁사 3개 요구에 LLM이 2개만 채우는 경우가 있고, **지어내
  채우지 않으므로** 부분 충족으로 보고합니다. 7건 중 4건이 그랬습니다. 빈칸을 채우면 28/28이
  되지만 문서에는 빈 경쟁사가 남습니다.
- **"표본 7건으로 충분한가요?"** → 충분하지 않습니다. 주제당 1회라 **주제 차이와 실행 편차가
  분리되지 않습니다.** 지금은 분포의 폭을 보는 용도입니다.

## p3 — 에러율 · 완주율 (25초)

### 제목
**"실패를 숨기지 않는다 — 그리고 실제로 하나 찾았다"**

### 슬라이드

| 항목 | 실측 |
|---|---|
| `run_status` | **7/7 `success`** · 폴백 0 · 실패 노드 0 |
| KOSENA Agent 4종 완주율 | **각 7/7** |
| 반복 미충족 항목 | `doc_length` **7/7**(구조적) · `competitors_3_2_1` **4/7**(LLM 편차) |
| 품질 게이트 | **0/7 통과** — 게이트가 작동한 결과 |
| 검색 완전 차단 시 | Agent **4/4 완주** · KOSENA **26/28** — 출처 항목만 미충족 |

**⚠️ 발표 전날 찾아 고친 결함 1건**

| | |
|---|---|
| 증상 | UI로 실행하면 KOSENA **11~12/28**, 스크립트로 측정하면 **26~27/28** |
| 원인 | 그래프 밖 State 병합에서 reducer 필드 5개 중 **`kosena` 하나 누락** → 마지막 노드의 10키만 남음 |
| 왜 안 잡혔나 | **두 실행 경로를 대조하는 테스트가 없었다** (테스트 667개 통과 상태) |
| 조치 | 그래프 안과 같은 reducer 재사용(2행) + 경로 대조 회귀 테스트 8개 → 실 LLM UI 관통 **27/28** |

### 나레이션 (약 140자)
> "7건 모두 완주했고 폴백은 0입니다. 검색을 **완전히 차단해도** Agent 4개가 완주하고 출처
> 항목만 미충족이 됩니다. 그리고 **발표 전날 실제 결함을 하나 찾았습니다** — Agent는 완주하는데
> 산출물이 State 병합에서 사라져, UI와 스크립트가 다른 값을 내고 있었습니다. 원인을 특정하고
> 고친 뒤, **두 경로가 일치하는지 검사하는 테스트**를 추가했습니다."

### 왜 이걸 먼저 말하는가
숨기면 약점이 되고, 먼저 말하면 **검증 능력의 증거**가 된다. `run_status`가 `success`이고 폴백이
0인 실행에서 `state.kosena` 키 개수와 `timing_events`로 원인을 좁혀낸 과정 자체가 이 프로젝트가
주장하는 "정확한 보고"의 실례다.

### 예상 질문
- **"품질 게이트를 통과 못 하는데 쓸 수 있나요?"** → 게이트는 **자동 출판** 기준입니다. 사람이
  검토·보완하는 **초안**으로는 쓸 수 있고, 무엇이 부족한지를 점수·major 이슈·근거 충족률로
  항목화해 줍니다. 임계값 자체가 **사람 기준선 보정 전 잠정값**(`calibrated: False`)입니다.
- **"그 결함이 측정값을 무효로 만들지 않나요?"** → 아닙니다. 측정은 결함이 없던 경로(`/run`)로
  했고 Agent·프롬프트·판정 로직은 손대지 않았습니다. **다만 "UI로 실행해도 같은 값이 나온다"는
  것은 이 수정 이후에야 사실이 되었습니다.**

## p4 — Evidence · 사실검증 · KOSENA 28항목 (25초)

### 제목
**"근거는 남기고, 모르는 것은 모른다고 남긴다"**

### 슬라이드 (좌: 근거 / 우: KOSENA)

**근거 · 검증** (도판 `05-evidence-verify.mmd`)

| 항목 | 실측 |
|---|---|
| 근거 총량 | 7건 합계 **117건** |
| `retrieved_at` | **117 / 117 전건 기록** |
| `published_date` | 25 / 117 (21%) — 검색이 줄 때만, 없으면 **'미상'** |
| 출처 우선 정렬 | 정부·공공 → 학술 → 언론 → 커뮤니티 순으로 프롬프트에 싣는다 |
| 검증 범위 | **`search_snippet_only`** — 검색 요약 기준, URL 원문 미검증 |
| 근거 확인율 | **0.20 ~ 1.00** (표준편차 0.30) — **미해결 과제** |

**KOSENA 28항목** (자체점검은 `app/services/kosena.py`, **결정적·LLM 없음**)

| 모듈 | 충족 |
|---|---|
| M1 산업·비즈니스 모델 | **8 / 8** |
| M2 데이터 기반 기획 | **10 / 10** |
| M3 개발 로드맵 | **6 / 6** |
| 공통 | 3 ok · 1 부분(`doc_length`) |

### 나레이션 (약 145자)
> "근거 117건 **전부에 조회 시점**이 있습니다. 발행일은 검색이 줄 때만 채우므로 21%이고,
> **모르는 것은 '미상'으로 둡니다.** 검증 범위는 검색 요약 기준이고 URL 원문은 재검증하지
> 않습니다. 그리고 근거 확인율이 0.2에서 1.0까지 흔들립니다 — 검증 Agent가 주장을 매번 새로
> 추출하기 때문이고, **미해결 과제로 기록했습니다.**"

### ⛔ 금지
- "각 KOSENA 주장마다 출처를 검증했습니다" → **실행 전체의 출처 존재 검사**다. 항목별 근거
  연결은 **미구현**이고 문서 부록에도 그렇게 적혀 있다
- "출처를 우선 수집합니다" → **우선 정렬**이다. 공식기관 도메인을 따로 검색하지 않는다
- "`unsupported`는 거짓이라는 뜻" → **'수집한 근거에서 확인하지 못함'** 이다

### 예상 질문
- **"근거 확인율이 흔들리면 게이트 판정도 흔들리는 거 아닌가요?"** → 그렇습니다. 확인율이
  게이트의 `evidence` 판정에 쓰이므로 **판정에 운이 섞입니다.** 주장 수가 5건 내외라 한 주장에
  0.2씩 움직이는 구조적 문제이고, 미해결로 기록했습니다.
- **"왜 항목별 근거 연결을 안 했나요?"** → 코드가 "이게 TAM의 근거겠지"를 **추론해서** 부록을
  만들면 그것도 허위입니다. 확실하지 않은 연결을 만드는 대신 미구현으로 남겼습니다.

## 이 섹션 전체를 관통하는 문장

> **"확인되지 않은 내용을 임의로 채우지 않고, 실패와 불확실성을 결과에 그대로 반영합니다."**

p2의 경쟁사 편차, p3의 게이트 0/7과 발견한 결함, p4의 '미상'과 미해결 과제가 **모두 같은
한 문장의 사례**다. 05를 마칠 때 이 문장을 한 번 더 말하면 04까지의 기술 설명이 하나로 묶인다.
